# 普通玩家背景遊玩評估計畫

制定時間：2026 年 11 月 6 日。目標版本：growth-v1.1，本機分支 codex/gameplay-v1-ready。

## 目的與固定範圍

檢查普通新玩家能否看懂目標、完成原本訓練、拿到正確獎勵、做出有作用的養成選擇，再回到下一輪。採用背景執行的真實瀏覽器及 API；不需要使用者看著逐頁點擊。

不修改題目、題組、正解、原判分、原發牌約束。不替玩家加錢、加經驗、加能量或跳等。一般流程的資料只能經原本玩家 API 產生。資料庫觀測使用唯讀查詢。較長時間的成長推算與真實請求紀錄分開。

自動測試可以證明流程、資源與目標是否成立，不能代替真人留存或主觀樂趣的證據。報告不使用「已證明玩家會一直玩」等說法。

## 一、怎樣判斷畫面與背後程式碼是同一件事

每個操作都建立同一條證據鏈：

1. 畫面：無頭 Playwright 開啟實際 Nginx 前端，以可見文字、語意角色與啟用狀態找到控制項，不直接呼叫 React 事件。
2. 操作：經真實按鈕送出；記錄操作前後 DOM、畫面截圖及主控台錯誤。
3. 傳輸：監看實際網路請求的路徑、方法、狀態與非敏感回應；禁止攔截後偽造成功回應。
4. 伺服器：對照路由、領域服務及資料表；以唯讀 SQL 核對局次、獎勵收據、資源與流水。
5. 回到畫面：比對回應數值與頁面數字，再重新整理確認。API 成功而畫面沒更新仍算失敗。

大整數用十進位字串與 BigInt 精確比對。獎勵驗算從收據公開的基礎值與倍率重新計算，不以再次呼叫結算函式當作正確答案。

| 玩家看到的流程 | 前端來源 | API／規則來源 | 必須核對的資料與畫面 |
| --- | --- | --- | --- |
| 回房間、找下一個目標 | 房間頁與 RoomStage／RoomScene | 玩家經濟與養成查詢 | 畫面入口可見，目標符合當前餘額與工具狀態 |
| 訊息判讀逐題送出與揭曉 | useQuiz、QuizReveal、題組頁 | quick.py 的 deck／answer／complete | 同一 QuizSession、五種原題型、原揭曉、一次結算 |
| 領取本輪資源 | QuizSummary、RewardBreakdown | progression.service.settle_reward | reward_context、reward_receipt、progression_ledger、User 與 player_growth 一致 |
| 起始配裝、強化、再訓練 | progression.tsx、useEquipment | equipment 路由、倍率計算 | player_equipment／equipment_loadout、花費、生效倍率與下一局收據 |
| 解鎖不同工具、有限槽取捨 | progression.tsx、useProgression | progression 路由與容量規則 | 能量扣除一次、同家族限制、槽滿提示、原局快照不被改寫 |
| 寵物羈絆、房屋與長期收藏 | LongTermGrowth、房屋頁 | collections.py、資產經濟路由 | 資源不足狀態、真實扣款、收藏等級與展示、重載保存 |
| 當期位置、追趕其他玩家 | leaderboard.tsx | seasons.py、collections boards | 今日實際入榜條件、我的位置、與上一名差距；未達資格不能誤報 |
| 再來一輪與中途返回 | useQuiz、結算頁 | 原局與下一局 API | 新 session、無重複領獎、返回後有可操作目標 |

實作時會將上述類別補上實際命中的檔名、請求、session／receipt ID 與截圖檔名，形成可回查的逐步紀錄。

## 二、三種測試分開報告

### A. 畫面與流程驗證

在目前完整 Docker 環境，建立新的普通玩家。手機 390×844 與桌面 1280×900 皆檢查；遊戲起始錢包必須是原預設 1,000、養成經驗和能量為零。

背景瀏覽器完成：註冊或正常帳號建立、登入、房間、起始配裝、完整原題組、結算、強化、再一輪、解鎖第二家族、配裝取捨、寵物、榜單、回房間。能做的養成以正常收入達成，達不到的記錄剩餘缺口，不用管理 API 補資源。

觀察：錯誤按鈕是否被禁用、送出中是否防連點、題目是否先答後揭曉、結算後數字是否立即刷新、下一輪是否能開始、手機內容與主要按鈕是否可見。

### B. 正常請求的成長測量

三種自動作答腳本使用相同原始規則：

- 穩定答對：預定全部答對，測量完整獎勵下的成長上界。
- 中等表現：每十題預定七題答對，測量七成正確率附近的正常成長。
- 常有失誤：每十題預定四題答對，觀察低收入時是否仍有下一步。

每種先跑六輪原本五題題組，合計至少十八輪、九十題。再以需要的正常輪數驗證第二家族與一次寵物養成；總上限為每帳號二十輪。腳本答案可從唯讀的已發牌局與原題庫取得，用來控制正確率；這是測試策略，不聲稱是真人解題表現，也不將答案提供給產品前端。

核心指標：

- 第一次能做有作用的配裝／強化在第幾輪。
- 第一次核心升級、第二工具家族與寵物養成各需要多少輪、多少題。
- 每輪實得金錢、原訓練經驗、養成經驗、能量及裝備倍率。
- 強化前後每輪增益、花費與按相同基礎獎勵估算的回本輪數。
- 低正確率時是否出現「資源不夠、沒有目標、也不知道去哪賺」的斷點。
- 同一時點可做的有效選擇，以及是否有每次都壓倒其他選項的單一路徑。

實際腳本耗時、API 等待耗時及題目文字量分開記錄。不能把自動作答一秒算成真人讀題一秒。若估計分鐘數，會列出明確的每輪閱讀時間假設及範圍。

### C. 長期規則與推算

十四天賽季不靠更改玩家時鐘或灌完成紀錄假裝自然經過。以現行資格（至少五天、五十題每日訓練、速度榜正確率至少九成）核對 UI 說明及目前玩家狀態。

使用 B 的實際基礎收入，加上原精確公式，推算核心等級與有限槽的所需輪數。輸出「已實際跑到」及「依指定策略推算」兩欄。先前已完成的關帳／並行／重啟測試作為另外的可靠性證據，不冒充此次普通新手進度。

## 三、本輪設計驗收門檻

以下是本輪採用的產品設計標準，不是真人研究結論：

1. 第一次進入時，能找到一個立即可完成或清楚列出缺口的近期目標，不能只顯示很遠的核心十級。
2. 正常玩家前三輪內能完成至少一次有實際倍率效果的養成。現有起始資金可以強化，應明確告知花費與前後變化。
3. 每輪結算顯示本輪成長與至少一個具體下一步，入口真正可用；每日訓練維持原本每日限制。
4. 資源不足的按鈕與提示一致，不讓玩家按下後才用籠統錯誤告知不足。
5. 強化與配裝會改變下一局收益；已開的原局維持原快照。畫面、收據、資源帳與重新整理後結果全部一致。
6. 正確率下降時仍有可見練習入口與可理解的目標；不改題目、不用送錢掩蓋斷點。
7. 排行榜能清楚說明當期與永久資產的區別、未達資格的原因及下一步，不能把尚未入榜顯示成第一名。
8. 不出現未處理的主控台錯誤、獎勵重複發放或畫面資源顯示與後端不一致。

## 四、發現問題後的處理

先保留未修正的基線數據。依「阻斷流程／資料錯誤 → 近期目標不清楚 → 成長間隔過長 → 次要呈現」排序處理。

可直接修正範圍：目標提示、結算後養成入口、缺少資源的說明、狀態刷新、資源可負擔狀態與已存在獎勵的呈現。涉及養成曲線時先列出基線輪數與變更後目標，只改新增養成參數，不動原題庫、判分或原訓練經驗。

每個修正用同一套背景流程重跑。未更動的原題庫與判定檔案重新核對，修改涉及的檢查與完整前端建置必須通過；若改後端領域規則，補跑相關 PostgreSQL 測試。

## 五、交付物與完成條件

- 本計畫書，先於此次背景評估結果產生。
- 可重跑的背景評估程式，及執行環境／帳號策略說明。
- 三類玩家的逐輪數據、達成里程碑、成本與回本表。
- 畫面操作、實際請求、收據與唯讀資料庫核對的關聯紀錄；不保存密碼或 token。
- 手機與桌面關鍵畫面截圖、發現問題、修正內容與重跑結果。
- 更新後的可玩程式包與驗收報告，放到桌面。

完成標準是計畫中的正常流程已跑過、有具體數據、發現的範圍內問題已修正並重跑。不能僅交付「計畫已完成」或舊測試總數。
